# PrivaClip: Privacy and Security Architecture

## 1. Security Philosophy & Threat Model

Clipboard managers are uniquely sensitive utilities: they intercept and store everything a user copies, including:
- Passwords and two-factor authentication recovery codes.
- API keys, SSH private keys, and cloud credentials.
- Confidential legal, medical, or corporate communications.
- Personal identification details and financial records.

Most existing clipboard managers store clipboard contents in unencrypted SQLite databases or plaintext JSON files in `~/Library/Application Support/`, making them vulnerable to rogue processes, backup scraping, and unauthorized local access. Furthermore, many modern clipboard tools introduce cloud synchronization or analytics tracking, creating catastrophic data exfiltration risks.

### PrivaClip Threat Model & Commitments

| Threat Vector | Mitigation Strategy |
|---|---|
| **Data At-Rest Extraction** (Physical theft or disk inspection) | All clipboard records, rich text, and snippet data are encrypted with **AES-256-GCM** using a symmetric key stored in the Apple Keychain. |
| **Cloud Exfiltration / Network Sniffing** | **Zero-Network Architecture**: No network frameworks (`Network.framework`, `CFNetwork`) are linked. Inbound and outbound network entitlements are set to `false`. |
| **Password Manager Leaks** | Inspects pasteboard metadata for `org.nspasteboard.TransientType`, `ConcealedType`, and `AutoGeneratedType` markers and immediately drops them. |
| **Unencrypted Image Artifacts** | Copied images are encrypted with individual IVs and authentication tags into an isolated `ImageVault` with POSIX `0700`/`0600` permissions. |
| **Process Crash / Data Loss** | Writes are atomic (`write(to:options: .atomic)`). Corrupted files are never overwritten; they are quarantined with timestamps. |
| **Application Compromise** | Documented limitation: A process running with the user's privileges and debugging entitlements can read process memory. PrivaClip never makes false guarantees regarding memory isolation against a fully compromised user session. |

## 2. Cryptographic Specifications

PrivaClip utilizes Apple's native **CryptoKit** framework, leveraging hardware-accelerated AES instructions (AES-NI / ARMv8 Crypto Extensions) on Apple Silicon.

### 2.1 Encryption at Rest (AES-GCM-256)
- **Algorithm**: Advanced Encryption Standard in Galois/Counter Mode (AES-GCM).
- **Key Length**: 256 bits (32 bytes), generated via `SymmetricKey(size: .bits256)`.
- **Nonce (IV)**: 12 bytes (96 bits) cryptographically random nonce generated per encryption operation via `AES.GCM.Nonce()`.
- **Authentication Tag**: 16 bytes (128 bits) appended to the ciphertext to ensure tamper detection. Any bit modification results in authentication failure during decryption.
- **Payload Structure**:
  ```
  [ 12 Bytes: Nonce ] + [ N Bytes: Encrypted Ciphertext ] + [ 16 Bytes: GCM Auth Tag ]
  ```

### 2.2 Password-Based Key Derivation for Backups (PBKDF2)
When exporting an encrypted backup (`.privaclip`), PrivaClip derives an AES-GCM encryption key from a user-provided passphrase using:
- **PRNG**: `CCKeyDerivationPBKDF` with `kCCPBKDF2`.
- **PRF**: HMAC with SHA-256 (`kCCPRFHmacAlgSHA256`).
- **Salt**: 32 cryptographically random bytes generated via `SecRandomCopyBytes`.
- **Iterations**: 100,000 rounds.
- **Derived Key**: 32 bytes (256 bits).

## 3. Keychain Integration & Key Lifecycle

The master encryption key is managed by `KeyManager.swift` via the macOS Keychain Services API (`Security.framework`).

### Keychain Attributes
```swift
let query: [String: Any] = [
    kSecClass as String: kSecClassGenericPassword,
    kSecAttrService as String: "com.privaclip.keys",
    kSecAttrAccount as String: "PrivaClipMasterKey",
    kSecAttrAccessible as String: kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly,
    kSecAttrSynchronizable as String: false
]
```

### Critical Security Properties:
1. **`kSecAttrSynchronizable = false`**: Explicitly prevents the master key from syncing to iCloud Keychain. The key never leaves the local device.
2. **`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`**: The key is accessible only after the user has unlocked the Mac after a restart, and is hardware-bound to the Secure Enclave / Secure Storage Component of the specific Mac.
3. **Automatic Key Migration**: If no key exists (e.g. on first launch), `KeyManager` generates a 256-bit symmetric key and commits it to the Keychain. If Keychain access is unavailable, a secure ephemeral key is generated in memory to prevent crashes, while alerting the user.

## 4. Sensitive Pasteboard Markers

Password managers and privacy-sensitive macOS apps tag their clipboard entries with specialized pasteboard types so clipboard managers know not to persist them.

PrivaClip strictly complies with the following markers in `ClipboardWatcher.swift`:

1. **`org.nspasteboard.TransientType`**: Content meant for immediate paste that should not be remembered.
2. **`org.nspasteboard.ConcealedType`**: Passwords or confidential data copied from password vaults (e.g. 1Password, Bitwarden).
3. **`org.nspasteboard.AutoGeneratedType`**: Automatically generated content (e.g. generated passwords or 2FA codes).
4. **`de.petermaurer.TransientPasteboardType`**: Legacy transient type used by older utility software.

When any of these types are present on `NSPasteboard.general`, PrivaClip updates its internal `changeCount` tracking to acknowledge the copy event, but completely discards the payload without writing it to memory history or disk.

## 5. Storage Isolation & Restrictive Permissions

PrivaClip stores its application data in:
`~/Library/Application Support/com.privaclip.app/`

### Directory and File POSIX Permissions:
- Root Application Directory: `0700` (`rwx------`) — accessible only by the current macOS user account.
- `history.encrypted`: `0600` (`rw-------`) — owner read/write only.
- `snippets.encrypted`: `0600` (`rw-------`) — owner read/write only.
- `vault/` (Image Vault): `0700` directory containing `.enc` image blobs stored with `0600` permissions.

### Corrupted Data Quarantine
If `history.encrypted` or `snippets.encrypted` fails AES-GCM tag verification (e.g., due to an interrupted write or disk corruption), PrivaClip **does not overwrite the file**. Instead, it moves the damaged file to:
`history.encrypted.corrupted.<timestamp>`
This preserves forensics and potential manual recovery while creating a fresh, authenticated store.

## 6. Verifying the Zero-Network Guarantee

You can independently audit that the PrivaClip application binary cannot make network connections:

### 1. Inspect Linked Dynamic Libraries
```bash
otool -L build/PrivaClip.app/Contents/MacOS/PrivaClip
```
*Expected Result*: Contains only `/System/Library/Frameworks/` entries for `AppKit`, `Foundation`, `CoreGraphics`, `Security`, `Carbon`, `CryptoKit`, and `libSystem.B.dylib`. Neither `Network.framework` nor `CFNetwork.framework` are linked.

### 2. Inspect Entitlements
```bash
codesign -d --entitlements - build/PrivaClip.app
```
*Expected Result*:
```xml
<key>com.apple.security.network.client</key>
<false/>
<key>com.apple.security.network.server</key>
<false/>
```

### 3. Monitor Network Traffic
Run macOS `nettop` or Little Snitch while operating PrivaClip:
```bash
nettop -P -m tcp -m udp -c
```
PrivaClip will never appear as an active socket or attempt DNS resolution.
